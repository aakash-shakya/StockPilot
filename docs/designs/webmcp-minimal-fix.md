## Problem Statement

StockPilot is an agent-native inventory app (TanStack Start + Netlify DB Postgres + Drizzle) where the dashboard and a browser tab agent operate on the **same domain logic** (`src/server/inventory.server.ts` → `src/server/inventory.functions.ts` → UI server functions + WebMCP tools `src/lib/webmcp/tools.ts:1-33`). The promise is **threshold alert → agent decision → human YES**, not enterprise forecasting.

Today the WebMCP surface is **32 tools** (`READ 8 + ANALYZE 12 + CREATE 4 + MUTATE 4 + COLLABORATE 4`, `tools.ts:649`) but docs claim 12 (`AGENTS.md:72`, `README.md:10` stale). Tooling works, but hits three gaps for a warehouse/procurement manager in a 20-100 SKU shop who currently walks the floor with a clipboard at 6am:

1. **Spec correctness gap:** Only `readOnlyHint` emitted (`tools.ts:688`), `inputSchema` hand-written and drifts from Zod validators in `inventory.functions.ts` (float IDs pass, unbounded `days`, missing `required`/`additionalProperties:false`). No `outputSchema`/`structuredContent`, errors returned as `{"error":...}` text not `isError:true`, token cost ~10k/turn before data.
2. **Safety gap:** Consequential tools rely on prose “only after owner approved” but `approve_agent_action:632` injects `decidedBy:'human'` even when agent calls it — impersonation. No `elicitation`, no idempotency key, `receiveShipment:413` / `createReplenishmentProposals:1039` not in `db.transaction`, no rate-limit.
3. **Discoverability gap:** No prompts/resources, no client `getTools()` dogfooding, no pagination/cursor, `WebMcpProvider.tsx:7` no feature-detect or try/catch, `registered:true` set before loop (`tools.ts:674`) never resets on throw.

The question is: what WebMCP upgrades make the warehouse manager actually *trust and pay* for agent-driven reordering without turning StockPilot into a 75%-AI-enterprise ERP?

**Who they are today:** Warehouse/procurement manager at a 20-100 SKU retailer/brand (Q3 answer). KPI = fill rate / on-time supplier / cash tied in dead stock. Fired for stockout that kills a launch, promoted for freeing working capital while holding availability.

## Constraints

- **WebMCP spec stage:** Draft Community Group Report 26 Aug 2026, **Chromium-only** origin trial 149-156 (needs `<meta http-equiv="Origin-Trial">` token; Edge behind flag, Firefox/Safari no commitment). Ship `provideContext` removed Mar 2026, entry moved `navigator` → `document` Jul 2026 (both ship 150, old deprecated). Tutorials showing `provideContext` are stale — close tab.
- **Progressive enhancement required:** `src/server/inventory.server.ts` remains single source; TanStack Start `*Fn` work without WebMCP. Feature-detect `if('modelContext' in document)` never assume presence.
- **Token economics:** 100-500 tokens per tool definition; 32 tools ≈ 10k before conversation (Anthropic reported 134K → 5K after lazy-loading). Must stay under 3k/10 tools or introduce search + execute.
- **Trust boundary:** Permissions Policy `tools` gates cross-origin iframe `allow="tools"`; secureContext only; tool names `^[a-zA-Z0-9_.-]{1,128}$`; abort via `AbortSignal`.
- **Stack guardrails:** Drizzle migrations auto-applied at deploy (`netlify/database/migrations` never hand-DDL per `AGENTS.md`), `noUnusedLocals` strict, `.js` extensions on relative imports, Tailwind 4.

## Approaches Considered

### Approach A: Minimal Viable Spec + Safety (CHOSEN)
  Summary: Tighten 32-tool surface to spec without breaking it. Hand-tighten or code-gen `inputSchema` from Zod, emit full annotations, fix error contract + human impersonation, leave tool count and flows intact. Ships this week.
  Effort: S (human: ~1 day / CC: ~2 hrs)
  Risk: Low
  Pros:
    - Keeps promise to any early scripter — no tool renamed or removed, docs still truthful after count fix; token cost acknowledged but contained.
    - Four annotation fields + `isError` make Claude Connector/host auto-approve correct (read-only no dialog, destructive red) — unlocks directory submission today.
    - Server gate removes impersonation hole without changing UX — one line in `decideAgentAction`.
  Cons:
    - Still 32 tools → 10k token tax remains; does not solve token economics or introduce prompts/resources.
    - Hand-tightened schemas drift again unless `zod-to-json-schema` adopted next phase — requires discipline.
    - Elicitation still prose-based — agent could still call `approve_purchase_order` after incorrectly inferring “owner said yes”.
  Reuses: existing `inventory.functions.ts` Zod validators, `@mcp-b/global` already installed, `agent_actions` table + `AgentActivityPanel` live store, `__root.tsx:52` `router.invalidate()` push.

### Approach B: Ideal Architecture — 7 Tools + Prompts/Resources/Elicitation
  Summary: Collapse 32→7 core tools, add `outputSchema`/`structuredContent`, `registerResource`/`registerPrompt`, `elicitation/create`, pagination/cursors, idempotency `UNIQUE` column + `db.transaction`, feature-detected provider, token-budgeted payloads via resource_links.
  Effort: M (human: ~1 week / CC: ~6 hrs)
  Risk: Medium — collapsing is breaking change; need `deprecated` aliases + versioned names.
  Pros:
    - Cuts token tax 10k → ~2k, enables lazy `resource://` for large payloads (`get_inventory_movements limit 50` → link) and push `resources/subscribe` on `inventory://health`.
    - Prompts make 3-5 step workflows one slash command (`/weekly_replenishment_review` → `whatShouldIWorryAbout` → `buildReplenishmentPlan` → `propose`) — user-controlled, not model-invented.
    - Elicitation moves consequential gate from description to deterministic form (`confirm:boolean`); `structuredContent` gives typed JSON to clients that read it, text fallback for others.
  Cons:
    - Requires new columns/migrations (`idempotency_keys`, cursor), new files `src/lib/webmcp/resources.ts`/`prompts.ts`, versioning/alias table, and updating `agent-tools.tsx` catalog — more migration risk.
    - Elicitation not universally supported (Claude Desktop today) — need fallback to text ask.
    - Origin trial still Chromium-only; declarative `<form tool*>` still TODO in spec — imperative stays primary.
  Reuses: `zod-to-json-schema` for both `inputSchema` and `outputSchema`, `BrowserMcpServer.registerResource/Prompt`, existing `riskForProducts` velocity logic.

### Approach C: Invisible Procurement OS — Subscribed + Policy
  Summary: Flip from polling dashboard to subscribed state. Agent subscribes to `resource://inventory/health` + `resource://pending-actions` (hourly diff), prompt encodes SOP with policy `auto-approve < $500 && reliability>80 else elicit`. Briefing pushes to phone; tab need not be open after approval.
  Effort: L (human: ~2 weeks / CC: ~10 hrs)
  Risk: High — policy engine + push infra + Permissions Policy cross-origin design; needs budget guard + rollback.
  Pros:
    - Achieves “whoa” moment: 6am proactive briefing without tab open — true wedge for 1-person warehouse who hates dashboards.
    - Turns WebMCP from query layer into policy OS; frames StockPilot as threshold→agent decision system, not ERP.
    - Sets convention while spec soft (trial until 156) — influences standard before it hardens.
  Cons:
    - Boldest → most to prove demand evidence and pay for; auto-approve policy must be explainable to auditors and reversible (`revert_movement` today blocks `sale`/`receiving` — needs relaxation).
    - Requires background subscription infra (Netlify scheduled function or client `setInterval` + `resources/subscribe` push — spec push not yet mature).
    - Over-anthropomorphizes for conservative buyers who want “alerts, not agents” — could scare early warehouse managers who still want clipboard trust.
  Reuses: `what_should_i_worry_about` as briefing core, `AgentActivityPanel` as push surface, existing `compare_suppliers` reliability score for policy threshold.
